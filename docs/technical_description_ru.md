# GigaEvoML - Техническое описание

## Краткое содержание

GigaEvoML - это распределенная система управления экспериментами машинного обучения, разработанная для масштабируемого параллельного выполнения ML-экспериментов. Архитектура системы позволяет единому Master API координировать несколько экземпляров Runner API, обеспечивая одновременное выполнение экспериментов на распределенных вычислительных ресурсах при централизованном управлении и мониторинге в реальном времени.

## Обзор архитектуры системы

GigaEvoML реализует микросервисную архитектуру с тремя основными компонентами, которые работают совместно для обеспечения масштабируемого управления экспериментами машинного обучения. Master API работает на порту 8000 и служит центральным сервисом оркестрации, отвечающим за координацию и управление экспериментами. Множественные экземпляры Runner API работают на портах 8001 и далее, предоставляя распределенные сервисы выполнения задач, которые запускают фактические эксперименты. WebUI работает на порту 7860, предлагая пользователям браузерный интерфейс для создания экспериментов и мониторинга их прогресса в реальном времени.

## Параллельное выполнение с несколькими Runner

### Ключевая инновация: Масштабируемое управление Runner

Ключевым отличием GigaEvoML является возможность управления несколькими экземплярами Runner API из единого Master API, обеспечивая истинное параллельное выполнение экспериментов:

#### Динамическое развертывание экземпляров Runner

**Автоматическое управление экземплярами:**
Master API автоматически развертывает и управляет экземплярами Runner API в качестве Docker-контейнеров, обеспечивая бесшовное масштабирование. Каждый экземпляр Runner работает независимо с собственным выделенным набором рабочих процессов, обеспечивая изоляцию и управление ресурсами. Новые экземпляры могут быть добавлены динамически через изменения конфигурации без необходимости перезапуска системы, что позволяет гибко масштабироваться в зависимости от спроса.

**Масштабирование на основе конфигурации:**

```yaml
# Пример конфигурации runner
runner_config:
  max_workers_per_instance: 5 # Воркеры на экземпляр runner
  auto_initialize: true # Автоматическое развертывание контейнеров
  instances:
    local:
      host: "runner-api-1"
      is_local: true
    remote-1:
      host: "remote-server.example.com"
      is_local: false
    remote-2:
      host: "another-server.example.com"
      is_local: false
```

#### Интеллектуальное распределение нагрузки

**Умное назначение экспериментов:**
Master API поддерживает информацию о статусе в реальном времени для всех экземпляров Runner, обеспечивая интеллектуальное назначение экспериментов. Эксперименты автоматически назначаются доступным экземплярам с достаточной емкостью, обеспечивая оптимальное использование ресурсов. Алгоритм балансировки нагрузки учитывает текущую рабочую нагрузку и статус здоровья экземпляра при принятии решений о назначении. Неисправные экземпляры автоматически обнаруживаются и удаляются из активной ротации, поддерживая надежность системы.

**Мониторинг здоровья:**
Система реализует непрерывные проверки здоровья каждые 30 секунд для мониторинга статуса всех экземпляров Runner. Механизмы автоматического восстановления экземпляров запускаются при обнаружении сбоев, минимизируя время простоя и обеспечивая доступность системы. Поддерживается синхронизация статуса в реальном времени между Docker-контейнерами и базой данных, предоставляя точную и актуальную информацию о состоянии системы.

## Архитектура коммуникации

### Многоуровневая система коммуникации

GigaEvoML использует сложный многоуровневый подход к коммуникации:

#### 1. Уровень REST API (Прямая коммуникация)

Уровень REST API обеспечивает синхронное развертывание и управление экспериментами через прямые HTTP-вызовы между Master и экземплярами Runner. Этот уровень обрабатывает критические операции, включая инициализацию экспериментов, команды запуска и остановки, а также загрузку файлов. Он обеспечивает надежную коммуникацию для основных функций управления экспериментами, требующих немедленного ответа и подтверждения.

#### 2. Уровень обмена сообщениями Kafka (Координация, управляемая событиями)

Обмен сообщениями через Kafka обеспечивает асинхронную оркестрацию экспериментов и распространение статуса по всей системе. Система обмена сообщениями использует несколько специализированных топиков для координации различных аспектов выполнения экспериментов. Топик `experiment-config` обрабатывает новые конфигурации экспериментов, в то время как `experiment-prepared` управляет уведомлениями о готовности файлов и ресурсов к выполнению. События жизненного цикла эксперимента передаются через топики `experiment-started` и `experiment-stopped`, а `runner-status` предоставляет обновления о состоянии здоровья и доступности экземпляров.

#### 3. Очередь задач Redis (Распределение рабочей нагрузки)

Redis обеспечивает высокопроизводительное распределение задач по всем рабочим процессам в системе. Реализация очереди задач включает глобальную очередь задач, которая обеспечивает балансировку нагрузки по всем runners, в то время как очереди задач для каждого эксперимента поддерживают требования координации, специфичные для эксперимента. Статус в реальном времени кэшируется с TTL в один час для быстрого доступа, а регистрация воркеров и мониторинг heartbeat обеспечивают надежное назначение задач и отслеживание выполнения.

## Управление жизненным циклом эксперимента

### Четырехфазный конвейер выполнения

#### Фаза 1: Создание эксперимента

Жизненный цикл эксперимента начинается, когда пользователи отправляют эксперименты через интерфейс WebUI. Master API валидирует входящую конфигурацию эксперимента для обеспечения правильности и полноты перед сохранением в базе данных. Если обмен сообщениями Kafka включен, запись автоматически добавляется в топик `experiment-config` для уведомления других компонентов системы о новом эксперименте.

#### Фаза 2: Подготовка и развертывание

На этапе подготовки потребитель рабочего процесса обрабатывает конфигурацию эксперимента для определения требований и зависимостей. Необходимые файлы и ресурсы систематически подготавливаются и загружаются в соответствующие системы хранения. Master API затем выбирает оптимальный экземпляр Runner на основе текущей доступности и рабочей нагрузки, развертывая эксперимент на выбранном экземпляре для выполнения.

#### Фаза 3: Распределенное выполнение

Фаза распределенного выполнения начинается с создания Runner API очереди задач, специфичной для эксперимента, для управления координацией рабочего процесса. Воркеры выполняют задачи параллельно с использованием фреймворка GigaEvolve, максимизируя вычислительную эффективность. Мониторинг в реальном времени собирает метрики и отслеживает прогресс каждые 15 секунд, в то время как промежуточные результаты и визуализации генерируются непрерывно во время выполнения для предоставления немедленной обратной связи.

#### Фаза 4: Сбор результатов и финализация

Заключительная фаза включает сбор и обработку всех результатов эксперимента в комплексном формате. Результаты загружаются в хранилище MinIO с полными метаданными для будущих ссылок и анализа. Обновления статуса распространяются через все уровни коммуникации для обеспечения общесистемной согласованности, и эксперимент официально отмечается как завершенный в базе данных с полным сохранением аудита.

## Возможности параллельного выполнения

### Многоуровневый параллелизм

#### Параллелизм на уровне экземпляров

Каждый экземпляр Runner API может выполнять несколько экспериментов одновременно, обеспечивая горизонтальное масштабирование. Количество воркеров на экземпляр настраивается, со значением по умолчанию в пять воркеров, которое может быть скорректировано на основе доступных ресурсов и требований рабочей нагрузки. Воркеры независимо опрашивают глобальную очередь задач, что обеспечивает оптимальное распределение нагрузки по всем доступным ресурсам в системе.

#### Параллелизм на уровне задач

Каждый эксперимент разбивается на дискретные задачи, которые могут выполняться независимо и параллельно. Типичная последовательность задач включает клонирование и настройку репозитория, генерацию и конфигурацию кода, фактическое выполнение эксперимента, а также сбор и анализ результатов. Этот подход на основе задач позволяет различным стадиям экспериментов прогрессировать одновременно, когда позволяют зависимости.

#### Изоляция ресурсов

Каждый экземпляр Runner работает в собственном изолированном Docker-контейнере, обеспечивая полное разделение ресурсов и сред выполнения. Контейнеры обеспечивают независимые файловые системы и пространства процессов, предотвращая конфликты ресурсов между экспериментами. К каждому экземпляру могут применяться настраиваемые ограничения ресурсов, а изоляция сбоев гарантирует, что неудачи в одном эксперименте не могут повлиять на выполнение других.

## Функции масштабируемости

### Горизонтальное масштабирование

Система поддерживает горизонтальное масштабирование по нескольким измерениям. Новые экземпляры Runner могут быть добавлены просто обновлением конфигурации, позволяя системе расти в зависимости от спроса. Количество воркеров на экземпляр может масштабироваться независимо, обеспечивая точное распределение ресурсов на основе требований эксперимента. Поддерживается географическое распределение, позволяя развертывать runners на разных серверах или облачных регионах для оптимальной производительности и резервирования.

### Оптимизация производительности

GigaEvoML включает множественные стратегии оптимизации производительности по всей своей архитектуре. Асинхронная обработка с неблокирующим вводом-выводом обеспечивает эффективное использование ресурсов и предотвращает узкие места. Пулинг соединений для баз данных и Redis-соединений снижает накладные расходы и улучшает время отклика. Пакетные операции для взаимодействий с Redis обеспечивают высокую пропускную способность для обновлений статуса и управления задачами. Интеллектуальное кэширование с использованием Redis обеспечивает быстрый доступ к часто запрашиваемой информации о статусе и метаданным.

### Отказоустойчивость

Система реализует комплексные механизмы отказоустойчивости на нескольких уровнях. Многоуровневые проверки здоровья мониторят статус контейнеров, отзывчивость API и здоровье выполнения задач. Механизмы автоматического восстановления перезапускают неудачные экземпляры и задачи без ручного вмешательства. Система обеспечивает плавную деградацию, продолжая работать с уменьшенной мощностью при сбое отдельных компонентов. Выполняющиеся эксперименты могут быть восстановлены из контрольных точек, гарантируя, что прогресс не будет потерян во время системных прерываний.

## Архитектура хранения

### Многосистемный дизайн хранения

#### PostgreSQL (Метаданные и состояние)

PostgreSQL служит основной базой данных для хранения конфигураций экспериментов и информации о статусе на протяжении их жизненного цикла. Она управляет метаданными экземпляров runner, включая статус здоровья и доступность, поддерживая комплексный реестр всех компонентов системы. База данных хранит полную историю выполнения задач для целей аудита и анализа производительности. Системные журналы аудита сохраняются для обеспечения полной прослеживаемости всех операций и изменений состояния.

#### Redis (Кэширование и координация)

Redis обеспечивает высокопроизводительное кэширование и возможности координации по всей системе. Он управляет очередями задач и координацией воркеров, обеспечивая эффективное распределение рабочих нагрузок и отслеживание статуса задач в реальном времени. Кэширование статуса в реальном времени обеспечивает быстрый доступ к информации о состоянии экспериментов и системы, в то время как управление сессиями поддерживает пользовательский контекст и состояние аутентификации. Временное хранение данных в Redis поддерживает промежуточные вычислительные результаты и временное состояние системы.

#### MinIO S3 (Файловое хранилище)

MinIO обеспечивает S3-совместимое объектное хранилище для всех файловых данных в системе. Входные файлы данных и наборы данных хранятся эффективно с метаданными для легкого извлечения и организации. Результаты экспериментов и генерируемые артефакты сохраняются с комплексной индексацией для будущего анализа. Генерируемые визуализации и графики хранятся в стандартных форматах, доступных через WebUI, в то время как контрольные точки моделей и выходные данные обучения поддерживают воспроизводимость экспериментов и обеспечивают дальнейший анализ.

#### Локальная файловая система (Рабочие данные)

Локальная файловая система обеспечивает временное хранение рабочих данных во время выполнения эксперимента. Клоны репозитория GigaEvolve поддерживаются локально для быстрого доступа и для поддержки контролируемых версиями сред экспериментов. Временные файлы экспериментов создаются и управляются во время выполнения, предоставляя рабочее пространство для промежуточных вычислений. Локальные вычислительные результаты кэшируются для снижения сетевого трафика и улучшения производительности для часто запрашиваемых данных.

## Возможности интеграции

### Интеграция с фреймворком GigaEvolve

Система обеспечивает бесшовную интеграцию с фреймворком GigaEvolve через автоматизированные процессы клонирования и настройки репозитория. Эксперименты могут напрямую использовать движок выполнения `run_hydra.py` от GigaEvolve, поддерживая совместимость с существующими рабочими процессами. Интеграция поддерживает нативные системы конфигурации и параметров GigaEvolve, позволяя пользователям работать с знакомыми интерфейсами и методологиями. Нативная обработка форматов вывода GigaEvolve гарантирует, что результаты могут быть обработаны и отображены без дополнительных шагов конвертации.

### Интеграция с внешними системами

GigaEvoML интегрируется с внешними корпоративными системами через несколько вариантов подключения. Интеграция с GitHub обеспечивает безопасный доступ к приватным репозиториям с использованием Personal Access Tokens, поддерживая рабочие процессы совместной разработки. S3-совместимое хранилище MinIO облегчает интеграцию с корпоративным облачным хранилищем, обеспечивая бесшовное управление данными в существующей инфраструктуре. PostgreSQL с пулингом соединений поддерживает корпоративные требования к базам данных, в то время как конечные точки проверки здоровья обеспечивают интеграцию с корпоративными системами мониторинга и оповещения.

## Характеристики производительности

### Возможности пропускной способности

Возможности пропускной способности системы разработаны для масштабирования с доступными инфраструктурными ресурсами. Количество одновременных экспериментов ограничено только доступными экземплярами Runner и рабочими процессами, обеспечивая горизонтальное масштабирование для удовлетворения требовательных рабочих нагрузок. Емкость обработки задач может достигать тысяч задач в час на воркер, хотя фактическая пропускная способность зависит от сложности эксперимента и вычислительных требований. Операции передачи файлов выигрывают от высокоскоростной интеграции S3-совместимого хранилища, в то время как обновления статуса доставляются в реальном времени с задержкой обычно менее 100 мс.

### Эффективность ресурсов

GigaEvoML спроектирован для оптимального использования ресурсов по всем компонентам системы. Накладные расходы контейнеров минимизированы через эффективное использование Docker-контейнеров и совместное использование ресурсов. Сетевая коммуникация оптимизирована для эффективности, используя локальную коммуникацию, когда сервисы расположены совместно, и применяя оптимизированные протоколы для удаленной коммуникации.
