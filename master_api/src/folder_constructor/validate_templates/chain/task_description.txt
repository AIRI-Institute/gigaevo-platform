TASK DEFINITION – CARL CHAIN EVOLUTION

Problem Type: Evolutionary CARL Chain Design
Challenge: Design and optimize a CARL reasoning chain that generates high-quality solutions for the given task.

OBJECTIVE:
Implement and iteratively improve a JSON configuration of a CARL reasoning chain.
The chain must read the input data and guide the underlying LLM through a sequence of reasoning steps to compute the correct answer.

- Output of the program: A CARL chain configuration stored in CHAIN_CONFIG_JSON, executed by the helper module.
- Fitness: Accuracy of predicted answers on the evaluation dataset.
- Goal: Maximize the measured Accuracy.

INPUT–OUTPUT CONTEXT:
- Input: Each data sample has fields from the dataset.
- Output: The final answer extracted from the CARL chain's output.

CONSTRAINTS:
- You MUST keep the `entrypoint` function signature and return format unchanged.
- You MUST define a single variable `CHAIN_CONFIG_JSON: str` inside the evolve block.
- `CHAIN_CONFIG_JSON` MUST contain valid JSON describing the CARL chain:

  REQUIRED FIELDS:
  
  - "steps" (REQUIRED): List of step objects defining the reasoning chain. Each step object MUST contain:
    
    * "number" (REQUIRED, int): Sequential step number starting from 1. Defines the execution order 
      of steps in the reasoning chain. Steps are executed in ascending order of their numbers.
    
    * "title" (REQUIRED, str): Short descriptive name for the step (e.g., "Problem Understanding", 
      "Solution Computation"). Used for identification and logging purposes.
    
    * "aim" (REQUIRED, str): Clear statement of what this step should accomplish. Describes the 
      goal or objective of the step in the context of solving the problem. Guides the LLM's 
      reasoning direction.
    
    * "reasoning_questions" (REQUIRED, str): Questions that guide the LLM's reasoning process 
      at this step. Should help break down the problem and focus on relevant aspects. Can be 
      a single question or multiple questions separated by newlines or semicolons.
    
    * "dependencies" (REQUIRED, list): List of step numbers (integers) that must be completed 
      before this step can execute. Empty list [] means the step has no dependencies and can 
      run immediately. Used to define the execution graph and ensure proper ordering.
    
    * "step_context_queries" (REQUIRED, list): List of strings specifying what context information 
      should be retrieved for this step. Defines what information 
      is available to the LLM during step execution.
    
    * "stage_action" (REQUIRED, str): Detailed description of the action to be performed at this 
      step. Provides specific instructions to the LLM about what operations, calculations, or 
      reasoning processes should be carried out. More detailed than "aim" and guides the 
      actual execution.
    
    * "example_reasoning" (REQUIRED, str): Example or template of how reasoning should proceed 
      at this step. Serves as a demonstration or pattern for the LLM to follow. Helps establish 
      the expected reasoning style and format.
  
  OPTIONAL FIELDS (at chain level):
  
  - "search_config" (OPTIONAL, dict): Configuration for context search strategies. Can include:
    * "strategy" (str): Either "substring" or "vector" - defines how to search for relevant 
      context from previous steps or external sources.
    * "substring_config" (dict): Configuration for substring-based search (if strategy="substring").
    * "vector_config" (dict): Configuration for vector-based semantic search (if strategy="vector").
    If omitted, no advanced context search is performed.

- The entrypoint function returns only the chain configuration - execution happens in validate.py.

FAILURE MODES:
- Invalid JSON (not parseable).
- Missing required fields for CARL steps.
- Reasoning chain that does not lead to correct answers.

EVALUATION FRAMEWORK:
- Performance is evaluated by accuracy and auxiliary metrics.
- Fitness = Accuracy on the train split; val_fitness = Accuracy on the validation split.
- Higher fitness → better chain.

OUTPUT FORMAT:

The entrypoint function is FIXED and must NOT be changed.
The entrypoint only returns the chain configuration - execution happens in validate.py.
